トークンで担保していること

フォーカスの可視化

--state-focus-ring を 3px で全操作要素に適用。:focus-visible を使うのでマウス操作では出ず、キーボード操作時のみ表示されます。outline: none だけを書くことは禁止です。

タッチ対象の大きさ

--control-height-lg が 44px。タッチ操作する要素はこれを下回らないこと。隣接する対象の間隔は --space-2（8px）以上空けます。

動きの抑制

prefers-reduced-motion を CSS 側で処理済み。前庭障害のある方に配慮し、アニメーションとトランジションが無効化されます。

拡大への耐性

文字サイズは全て rem 基準なので、ブラウザの文字サイズ設定と 200% 拡大に追従します。px 固定のフォントサイズは使いません。

操作部品の境界

--color-border-control を新設し 3:1 を確保。装飾的な区切り線（--color-border-default）とは別トークンです。入力欄の枠は「そこに部品がある」ことを示す情報なので、基準が異なります。

行長の上限

--container-prose が 68ch。一行が長すぎると次の行の頭を見失いやすく、読字障害のある方に特に影響します。

実装側で担保すること（トークンでは守れない）

見出しレベルの順序、ランドマーク要素、フォームのラベルとエラーの関連付け（aria-describedby）、ステータス更新の読み上げ（aria-live）、キーボードのみでの操作完遂。特に監視系プロダクトでは、画面が自動更新される値を aria-live="polite" で伝える設計が要ります。

プロダクト用の色相

elchika inc. 自身は常に青です。以下は将来のプロダクトが選ぶための在庫で、すべて寒色弧（222°〜334°）に置いています。暖色はステータスの意味に予約されているためです——success の緑、danger の赤、warning の橙、そしてブランドの黄がすでにその側を占めており、プロダクト色をそこに置くと信号として読まれます。

各ランプは青と同じコントラスト特性になるよう数値を解いています。どの色相を選んでも可読性は変わりません（600 = 白に対し 5.7:1、400 = 暗い面に対し 5.6:1、700 = 白に対し 10.2:1）。

使うときの規則

上から順に取る

好みで選ばず、表の順番で割り当てます。3つ目までは ΔE 20 以上あるので安全です。

indigo は最後の手段

青との最悪ケースが ΔE 7.4 で、1型・3型では実質見分けがつきません。elchika 本体と並ぶ場面があるなら使わないでください。6色目が必要になった時点で、色による識別自体を見直すほうが健全です。

上書きするのは5個だけ

プロダクトは --brand-* のみを差し替えます。ステータス色・ニュートラル・書体・余白はコーポレート固定のままです。

色は補助であって主役ではない

色相を割り当てても、プロダクトの識別をそれだけに頼らないこと。ワードマークとプロダクトマークが主で、色は補強です。

--chart-*

データビジュアライゼーション

グラフの色はブランドカラーとは別の要求を持ちます。線は細く、複数が同時に並び、値の大小を表す必要がある。ここでは3種類のスケールを定義します。

規則

系列は5つまで

超えたら色を足さず、凡例をやめて線に直接ラベルを置きます。人が同時に照合できる凡例の数には限界があります。

色と破線を必ずセットで使う

系列1は実線、2以降はそれぞれ固有の破線。色が失われても順序と区別が残ります。

ステータス色は帯にだけ使う

系列の線に赤や緑を使わないこと。データの識別子と状態の信号が混ざります。

連続スケールは明度を単調にする

虹色スケールは値の順序が読めず、色覚特性下では破綻します。

実装側で担保すること

Decisions

決めたことと、その理由

後から「なぜこうしたか」を辿れるように残します。トークンを更新するときは、ここに追記してください。

# このページを編集したら

ブランドカラーは青がメイン、黄色がサブ

「知的で好奇心旺盛」という方向から。青が構造を担い、黄色は発見の一点にだけ灯す。補色関係でコントラストが強く出るため、黄色は面積を絞って使います。

黄色の背景に青文字は使わない

バッジのような小面積では違和感が出るため、黄色の背景には黄系の濃色を乗せて同系色でまとめます。青は構造側（ボタンなど）に留めます。

書体は IBM Plex スーパーファミリー

和文・欧文・等幅が同じ設計思想で揃うこと、そして研究機関・技術文書の血統を持つことから。Mono を「ラベルと数値」の専用レイヤーに割り当て、これをブランドの署名的な装置とします。

検討したが不採用：他の和文書体

Zen Kaku Gothic New / Murecho / M PLUS 2 / BIZ UDPGothic / Noto Sans JP を比較。実測すると字幅は異なるものの、和文ゴシックというカテゴリ内では知覚できるほどの差が出ないと判断。明朝見出し（Zen Old Mincho）はカテゴリ外で差は出るが、プロダクトUIで浮くため見送り。

和文の行間は 1.75、本文は 16px

欧文の既定値 1.5 は和文では詰まって見えるため。本文サイズも 15px では漢字が潰れるので 16px を基準に置きます。小さい和文は字間をわずかに開けて +0.02em。

更新される数値は等幅数字で組む

Manako のような監視系プロダクトでは値がその場で書き換わるため、桁幅が揃わないと数字が横滑りします。実利のある決定です。

Tailwind では spacing / fontWeight / screens を上書きする

extend ではなく上書きにすることで、p-7 や font-bold のような系外の値が書けなくなります。デフォルトを残すとトークンが形骸化するためです。

プロダクトはプリミティブだけを上書きする

セマンティック層を各プロダクトが直接上書きすると、ライト・ダーク・状態の組み合わせで定義が増え続けて破綻します。上書き可能な面を --brand-* の5個に限定し、セマンティック層はその参照だけで値が決まる構造にしました。1プロダクト＝5行で済みます。

黄色のアクセントはコーポレート固定

青の色相だけがプロダクトごとに変わり、黄色・書体・余白・ニュートラルは共有されます。「別プロダクトだと分かるが、同じ会社に見える」状態を作るのが狙いです。

ステータス色は上書き禁止

緑と赤の意味がプロダクトごとに変わると、監視・配信という文脈では実害が出ます。ブランド表現ではなく、安全に関わる語彙として扱います。

スペックページを唯一の正とし、CSSは生成する

これまで design-tokens.html / tokens.css / brands.css / tailwind.config.js を手で同期させていましたが、実際に一度ズレました。build-tokens.mjs がスペックページからCSSを生成し、未定義トークンの参照とコントラスト基準を検証します。不合格なら終了コード1で落ちるので、CIに載せればそのままマージを止められます。生成物は直接編集しないでください。

密度は専用トークンに閉じ込める

--space-* を丸ごと縮めるとレイアウト全体が動きます。密度が触るのは行の高さ・セルの余白・コントロールの高さだけで、適用範囲も表・一覧・ツールバーに限定しました。文章や LP には効きません。compact の行高 32px はタッチ対象の最小 44px を下回るので、ポインタ環境限定です。

組版は言語ごとに切り替え、色と余白は共有する

和文向けに調整した行間1.75と字間+0.02emを英語に当てると、間延びします。:lang(en) で組版側だけを再調整しました。和欧の間の四分アキは組版の仕事なので、文言に手動でスペースを入れることは禁止です。

文言も設計材料として記録する

エラーは謝らず、何が起きたかと次の一手を書く。ボタンの動詞と結果の文言を一致させる。実装の都合ではなく利用者の語彙で呼ぶ。この3つを軸にしました。決めておかないと書く人ごとに揺れます。

グラフの系列は5つを上限にする

6つ目は青と indigo が判別できなくなるため用意していません。系列が増えたら色を足すのではなく、凡例をやめて線に直接ラベルを置きます。人が同時に照合できる凡例の数には限界があるので、これは色の問題であると同時に読み取りの問題です。

系列は色と破線をセットで使う

ステータスに記号と形を併用したのと同じ考え方です。色が失われても区別が残るようにしました。グレースケールのシミュレーションを入れてあるのは、色覚特性だけでなく、プロジェクタや印刷でも同じ問題が起きるからです。

ステータス色は帯にだけ使い、線には使わない

系列の線に赤を使うと、その系列自体が「エラー」に見えます。データの識別子と状態の信号は、適用する場所で分けました。

発散スケールは赤緑ではなく rose と blue にする

一般的な発散スケールは赤↔緑ですが、この2色はステータスの意味を持つうえ、色覚特性下で最も見分けにくい組み合わせです。ブランドの色相在庫から2色を取りました。

プロダクト色相は寒色弧に限定する

暖色域は success の緑・danger の赤・warning の橙・ブランドの黄がすでに占有しており、そこにプロダクト色を置くと信号として読まれます。222°〜334° の寒色弧に限定しました。制約の副作用として、どのプロダクトもコーポレートの青の親戚に見えます。

色相は目視でなく色差の計算で選んだ

候補を色覚シミュレーション（1型・2型・3型）に通し、相互の色差とステータス色との色差を計算して選定しました。最初に用意した8色相のうち teal と azure は success の緑と ΔE 3.1 まで接近しており、目視では気づけない衝突でした。除外しています。

indigo は在庫に含めるが、実質使えない

青との最悪ケースが ΔE 7.4 で、1型・3型では見分けがつきません。6色目が必要になった時点で、色による識別自体を見直すべきというサインとして残しています。

全色相を同一のコントラスト特性で生成する

各段の明度を、コーポレートの青と同じコントラスト比になるよう数値的に解いて決めました。どの色相を選んでも可読性が変わらないため、プロダクトごとにアクセシビリティを再検証する必要がありません。

コントラストは実測して不合格を修正した

目視で判断せず全組み合わせを計算したところ、4件の実際の不合格が見つかりました。text-muted（3.04）、accent-text（4.37）、そして入力欄の枠として使っていた border 系の2件です。それぞれ色相を保ったまま基準を満たす値に修正しています。

装飾の罫線と、部品を示す枠は別トークンにする

カードの区切り線は装飾なので 3:1 は不要ですが、入力欄の枠は「そこに部品がある」ことを示す情報なので 3:1 が要ります。同じ「線」でも基準が違うため、--color-border-control を分けました。1本の値で両方を満たそうとすると、装飾線が濃すぎるか、部品の枠が薄すぎるかのどちらかになります。

warning は黄ではなく橙にする

黄はブランドのアクセント色なので、警告に同じ色を使うと「これはブランドの強調か、警告か」が判別できなくなります。橙に分離しました。ブランドカラーを持つ以上、ステータス色は避けて設計する必要があります。

ステータスは色・記号・形の3重で伝える

緑と赤は色覚特性のある方に最も見分けにくい組み合わせです。記号（✓ ! × i）と形（円・角丸・菱形）を併用し、色が失われても判別できる状態にしました。監視・通知系のプロダクトを持つ以上、ここは実利に直結します。

状態はコンポーネントごとではなく一度だけ定義する

コンポーネント×状態でトークンを切ると、コンポーネントが増えるたびに定義が掛け算で膨らみます。重ね色・押下・選択・無効・エラーを --state-* として共有し、各コンポーネントはそれとセマンティック層を参照する形にしました。監視ダッシュボードのように状態表示が多い画面ほど効きます。

重ね色は明暗を反転させる1つのトークンにまとめる

ライトでは暗く、ダークでは明るく重ねる必要がありますが、--state-tint の値を切り替えることで記述は1つで済みます。ダークはやや濃いめ（0.07 / 0.13）にしないと知覚できません。

例外としてコントロールの寸法だけはトークン化する

ボタンと入力欄の高さが揃わないのは最も目につく崩れです。粗い粒度の方針の中で、ここだけは共通の値を持たせます。lg の44pxはタッチ操作の最小快適サイズです。

全プロダクトがコーポレートの青を継承する

プロダクトごとに色相を振り分ける案を検討しましたが、「青がメイン、黄色がサブ」という当初の軸そのものが薄まるため不採用にしました。プロダクトの区別はワードマークとプロダクトマークが担当します。家族感は最大化される一方、色による識別は効かなくなるので、マーク側の設計が重要になります。

上書きの面と予備案を残す

--brand-* の上書き構造に加え、プロダクトごとの色相案（teal / violet / rose）も参考として残しました。色による識別が必要になったときに、構造から作り直さずに済ませるためです。使わないことと、使えないことは違います。なお Miseru の rose は danger の赤と系統が近いため、採用する場合はエラー表示と並べた確認が必要です。

既存プロダクトの現行テーマは参照しない

Manako などのLPにすでに配色がありますが、それに引きずられるとブランドの軸が後追いになります。トークン側を正とし、プロダクト側を寄せていきます。
